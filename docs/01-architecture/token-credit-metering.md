# 消耗计量与积分标定设计

> 2026-10-10。借鉴 DSH（DeepSeek Harness）`@deepseek-ai/dsh-token-meter` 的分桶计量模型，
> 解决 RelayGate「会话 token 消耗算不出、积分消耗估不准」的问题。

## 1. 问题根因（按影响排序）

| # | 根因 | 影响 | 修复 |
|---|------|------|------|
| 1 | `log/traffic.js` 的 `sanitize()` 用 `/token/i` 匹配键名脱敏，把 `totalTokens`/`promptTokens` 等计量字段打 `"***"` | **实测 2026-10-10 单日 1600 行日志的 usage 全部丢失**，统计 token 恒 0、费用恒 null | 数值/布尔不脱敏，仅字符串走 `maskSecret` |
| 2 | `sanitizeUsage` 只保留官方三字段，缓存读 token 被丢弃 | 无法区分「缓存命中输入」与「未缓存输入」——两者单价差 4~8 倍，费用系统性高估 | `peekUsageDetail` / `usageToLogFields` 抽出 `cacheReadTokens` |
| 3 | `estimateCost` 只有 tier 倍率（1/1.5/3/5/10）猜测口径 | 与官方账单误差可达数十倍 | 账单反向标定（见 §3） |
| 4 | 历史 `"***"` 行会被 `isMetered` 的 `!= null` 误判为已计量 | 覆盖率虚报 100% | `isMetered` 仅接受有限数值 |

## 2. DSH token-meter 借鉴了什么

DSH 的核心设计（`@deepseek-ai/dsh-token-meter` 0.2.0-rc.2，从 app.asar 解出研读）：

1. **四桶分层**：`uncachedInputTokens / outputTokens / cacheReadTokens / cacheWriteTokens`，
   互斥加和等于总消耗；提供方 usage 只有在「四桶能精确对上总量」时才被采纳
   （`normalizeUsage` 校验失败整条拒绝）。
2. **提供方 usage 为锚、启发式只兜底**：`measure()` 优先复用上次成功调用的提供方用量
   （usage anchor），只有 envelope 变化或总量低于启发式锚点时才重新估算。
3. **所有消费方读同一份 fold**：压缩、占用 UI、遥测共享同一测量，不各自算。

RelayGate 对应落点：

- 四桶模型 → `models/pricing-calib.js` 的三系数回归变量（cacheWrite 样本不足暂缓）；
- usage 锚点 → 项目原有「上游 usage 优先、tiktoken 补算标 `tokensEstimated`」已同构，未改；
- 单一测量源 → 全部费用计算收敛到 `models/rates.js#estimateCost` 一个入口。

## 3. 积分/token 标定（核心）

### 原理

把一次调用的积分建模为三桶 token 的线性函数：

```
credits = a·uncachedInput + b·output + c·cacheRead     （a/b/c 单位：积分/token）
```

用**官方账单**做最小二乘回归求 a/b/c。官方账单是唯一权威，回归让估算收敛到账单口径。

### 数据源（两路，自动合并）

| 源 | 粒度 | 数据形态 | 配对方式 |
|----|------|---------|---------|
| Trae 会话账单（`trae-usage-cache/`） | 逐会话 | 四桶 token + credits 同行 | 天然配对（`byModel` 单模型才行） |
| WB 客户端日志（`client-logs.js`） | 逐请求 | `providerData.usage` + `rawUsage.credit` 同行 | 天然配对，无需按时间猜 |

> WorkBuddy 官方账单接口只回 credit 不回 token；token 只能取自客户端日志，
> 而 `rawUsage.credit` 与 usage 在同一行，比「账单×日志按时间戳配对」可靠得多。

### 实测标定质量（2026-10，6176 会话 + 4936 请求）

| 模型 | 平台 | n | R² | 未缓存输入 | 输出 | 缓存读（积分/1k token） |
|------|------|---|----|-----------|------|----------------------|
| glm-5.3-flash | Trae | 780 | 1.000000 | 0.0160 | 0.0560 | 0.0046 |
| glm-5.3-flash | WB | 1162 | 0.999976 | 0.0114 | 0.0399 | 0.0033 |
| qwen3.8-flash | Trae | 582 | 1.000000 | 0.0320 | 0.1080 | 0.0040 |
| glm-5.3-flashx | Trae | 78 | 1.000000 | 0.0800 | 0.2800 | 0.0228 |
| deepseek-v4.1-flash | WB | 1129 | 0.945229 | 0.0270 | 0.0795 | ~0 |
| deepseek-v4-flash | Trae | 4730 | 0.896760 | 0.0573 | 0.1512 | 0.0060 |

R²=1 的模型可做到**逐会话账单精确还原**（预测误差 < 0.5%）；Trae 的 DeepSeek 系
因会话级聚合行有抹零/阶梯噪声 R² 偏低（WB 逐请求口径同模型 R² 0.94+ 可补）。

### 关键结论：标定键必须带平台

同名模型跨平台费率不同（glm-5.3-flash：Trae 未缓存输入 0.016/1k，WB 0.0114/1k，差 ~30%）。
标定键为 `trae:<normModel>` / `wb:<normModel>`，查找时按请求平台选表，
平台未命中再跨平台回退。

## 4. 链路改动清单

```
上游 usage（三平台形态）
  → dispatch.peekUsageDetail()        抽缓存读，裁官方三字段回客户端
  → traffic.usageToLogFields()        归一化为 promptTokens/completionTokens/cacheReadTokens
  → logRequest() → sanitize()         数值不再被 "token" 正则脱敏
      ├─ estimatedCost = rates.estimateCost(model, pt, ct, {cacheRead, platform})
  → stats.js / stats-cache.js         按 cacheReadTokens 传参重算
  → /v1/admin/stats/pricing-calibration   标定系数与拟合质量可视化
```

`estimateCost` 三级兜底：**账单标定 → catalog.consumption_rate → tier 倍率**。

## 5. 丢失数据能否恢复（2026-10-10 核查）

**结论：分两种情况——数字字符串可完整还原，真脱敏行不可逆。**

核查后发现历史日志的 token 字段有**三种形态**，此前被混为一谈：

| 形态 | 举例 | 出现日期 | 可还原性 |
|------|------|---------|---------|
| number | `50918` | 正常日志 | ✓ 本来就可用 |
| 数字字符串 | `"49569"` | ~09-15 ~ 09-30（旧版落盘格式） | ✓ **可还原**（`numTok` 已接受） |
| `"***"` | `"***"` | 10-06~10-10（脱敏缺陷期） | ✗ 原值从未落盘 |

早先的 `numTok` 一律拒绝字符串，把 9 月每天 1000+ 行**可还原**的真实 token
判成了未计量（覆盖率虚低、估算缺位）。修复后 9 月数据完整恢复参与统计。

10-06~10-10 的 5121 行 `"***"` 不可逆。**每日成本/用量由官方账单补齐**
（覆盖 10-04 起全部日期），已接入 `/stats/daily` 的 `officialCredit` 字段，
前端「每日积分对照」表逐日并列。

### 为什么不能把账单 token 回填进 traffic.jsonl

账单是**按会话/按请求聚合**的，与网关逐请求行没有稳定的一对一映射
（Trae 一行 = 一次完整会话含数十次调用）。强行回填会伪造出错误的逐请求明细。
因此采用**并列展示**而非回填——这也是 `officialCredit` 与 `estimatedCost`
分列两栏、不合并求和的原因。

## 5.1 历史估算成本的两个量纲错误（本轮发现并修复）

排查「每日积分对照」表 9 月差异 615%~904% 时，发现估算链路有**两个**
被固化进历史数据/统计路径的口径错误：

1. **tier 兜底费率量纲错误（虚高约 97 倍）**
   `TIER_RATE_FALLBACK = {5: 1}` 的语义是「1 倍」，但被 `estimateCost`
   按「1 积分/千 token」使用；账单实测约 0.0103 积分/千 token。
   实测 09-27 落盘的 `estimatedCost` 合计 241,539，当日账单仅 1,976.61。
   修复：`costOf` 一律按当前标定系数重算，**不采信落盘值**；
   落盘的旧 `estimatedCost` 字段不再被统计路径读取。

2. **缺 cacheRead 时按全未缓存计价（虚高约 7 倍）**
   9 月日志的 usage 不含 `prompt_tokens_details.cached_tokens`，
   全部输入被按未缓存单价（0.058/1k）计价，而账单实测混合费率 0.0082/1k——
   当月缓存命中率约 90%。修复：这类行由 `costUpper` 标记为「上界」，
   前端在估算列加 ↑ 角标提示偏高。

修复后 30 日对照（网关估算 vs 官方账单）仍有天数差 ±100%，
但每个差异都能归因到明确的数据局限（token 缺失 / 上界行 / 入账滞后），
不再是两个错数的差。

### 「每日积分对照」表为什么只留 4 列

首版放了 7 列（日期/请求/网关Token/丢失行/网关估算/官方账单/差异）。
评审结论：请求数与丢失行是**诊断指标**，不是产品读数——它们已分别出现在
「计量覆盖率」卡和「Token 总量」卡里，重复列出且大部分为空，反而让人以为
表本身有数据问题。精简后每格都有值或明确的「—」。

三处「—」/状态文案各有明确语义，不再用同一个符号表达不同情况：

| 单元格 | 显示 | 含义 |
|--------|------|------|
| 官方账单 | `—` | 该日两路账单均无缓存（从未查过该日） |
| 官方账单 | 数值 | 有账单；若 Trae 侧为 0 则表示仍在入账滞后窗口内 |
| 网关估算 | `数据缺失` | 该日无可用 token（历史脱敏），**不是 0 消耗** |
| 网关估算 | `数字↑` | 含上界行（缺缓存读信息），估算偏高 |
| 差异 | `入账中` | Trae 账单未完整入账，全平台估算 ÷ 单平台账单会算出假差异 |
| 差异 | `—` | 单侧为 0 或数据缺失，比值无意义，不猜测原因 |

### 卡片信息架构的取舍

原布局把 5 张卡塞进 4 列网格，第 5 张（换算比）单独换行，视觉上像被遗落的附注。
重排原则：**一屏之内先答两个问题——花了多少积分、用了多少 token**。

1. **官方账单积分**（成本主读数，品牌色）——内嵌估算对照百分比，差异一眼可见
2. **Token 总量**（用量主读数）——三来源 + 缓存读占比 + 丢失警示
3. **换算比**（连接两者的桥）——回答「这些 token 值多少积分」
4. **计量覆盖率**（可信度）——回答「这个数字有多可靠」

四张卡各答一问，不再有落单项。原「本地估算成本」独立卡取消——
它是**对照口径**，放在主读数卡内部作对照行比单列一张大卡更符合它的地位
（单列时字号与官方账单相同，视觉上会被误读为同等权威）。

## 7. 已知边界

- **估算与账单的差异不全是误差**：估算 = 已计量 token × 标定系数，只在
  token 回传完整的日期才可比。差异来源有三：①当日大量请求未带回 usage（估算偏低）；
  ②账单入账滞后（账单偏低，Trae 尤甚，最近 1~2 天常为 0）；③回传的 usage 缺失
  缓存读细节（估算偏高）。「每日积分对照」表的差异率需结合这三条解读。
- **WorkBuddy 网关行数 > 账单请求数**（实测 240 vs 56）：网关每个上游调用记一行，
  账单只对成功计费调用入账。两者不是同一分母，不可直接相除。
- 标定数据滞后：Trae 账单日级入账、标定缓存 6h 复算；上游调价后最长 6h+1d 收敛。
- cacheWrite 桶：WB 客户端有 `prompt_cache_write_tokens` 但样本中恒 0，暂未入模。
- tiktoken 补算路径（`tokensEstimated=true`）仍是 OpenAI 分词器口径，只作趋势，
  其 estimatedCost 同样走标定系数但 token 本身有 ±10% 级偏差，界面应区分展示。
- Trae `DeepSeek-V4-Flash 正式版` 会话级样本噪声大（R²≈0.90），需要更准可在
  `readWorkbuddyRows` 启用官方账单×客户端日志时间窗配对（当前已用 rawUsage.credit 直配，无需此步）。

### 复现本轮修复的验证点

- `wb/` 前缀：`normModel('wb/glm-5.3-flash')` 必须等于 `normModel('glm-5.3-flash')`。
  修复前者归一为 `wb/glm5.3flash`，与标定键 `wb:glm5.3flash` 前缀不匹配 → 成本恒 null
  （实测让 WorkBuddy 全部请求估算为 0，7 日合计只有 143 而非 416）。
- 缓存读分桶：同一批 token 若忽略 `cacheReadTokens`，估算会高 4 倍以上
  （实测 391.66 vs 93.52）。
- `pricedModel`：虚拟模型行的 `r.model` 是 `vm/xxx`，费率表无此键；
  `costOf` 必须回退 `pricedModel` 或解析 `routedTo`。
- **数字字符串 token**：`numTok('49569')` 必须返回 49569（旧版落盘格式）。
  一律拒绝字符串会让 9 月数据「消失」；一律接受会让 `Number("***")`=NaN 污染。
  按「纯数字才接受」分流，配合 `isMasked` 单独计数真脱敏行。
- **tier 兜底费率量纲**：`TIER_RATE_FALLBACK` 不是积分口径（差 97 倍），
  统计路径不得读取日志里固化的 `estimatedCost`，必须按标定系数重算。
