# 已知限制与设计边界

本文记录**有意保留的限制**：每条含「现状 → 为什么这样 → 什么条件下该重新评估」。
目的是避免下一个维护者（或 AI 助手）把它们误当成 bug 顺手「修掉」，或误以为它们
已经有防护。

范围：本项目定位是**单人自托管工具**（跑在自己的机器上、只有机主一个用户）。
下面多条限制都是这个前提的直接推论。

---

## 一、安全边界

### L1. 加密密钥与密文同目录

- **现状**：`output/.trae-api/encrypt.key`（密钥）与 `output/.trae-api/trae-relay.db`
  （密文）同目录，仅靠文件系统权限隔离；未接入 OS keystore / DPAPI。
- **为什么这样**：单机自托管，同用户进程天然可读 DB（它还要提供 API 服务），
  密钥与密文分离只增加运维成本而不增加实际防护。
- **重新评估的条件**：接入多用户、或对同机其他低权限账户提供隔离时。

### L2. 登录密钥使用无盐 SHA-256

- **现状**：`kind=login` 的密钥按 `sha256(key)` 存储（`credentials/api-keys.js`）。
  访问密钥同理。密钥本体是 24 随机字节（192 bit），暴力破解不可行。
- **为什么这样**：高熵随机密钥不需要慢哈希；引入 argon2 只增加校验延迟。
  **但若你把 `ADMIN_KEY` 设成了短口令**，从 DB 泄露即可离线还原登录密钥。
- **建议**：`ADMIN_KEY` 使用 ≥ 20 字符的随机串（面板创建的首把登录密钥不受此限）。
- **重新评估的条件**：将来支持用户自选弱口令时。

### L3. `/health` 与 `/status` 免鉴权可见运行态

- **现状**：`/health` 无需任何凭据即可读取检查结果与池计数；`/status` 默认需鉴权
  （`STATUS_PUBLIC=true` 时免鉴权）。
- **为什么这样**：服务管理器与容器健康探针需要在无凭据的情况下判断进程状态。
  `/health` 只返回布尔与计数，不含路径、密钥材料或账号标识。
- **重新评估的条件**：把 `HOST` 改为非 `127.0.0.1` 暴露到网络时。

### L4. 默认监听 127.0.0.1，跨机访问无传输加密

- **现状**：默认只绑本机。若改 `HOST=0.0.0.0` 对外提供，HTTP 转发面为明文，
  Bearer 密钥在网络上可被嗅探。
- **为什么这样**：单机工具默认安全优先；跨机暴露属于用户的显式选择，
  已在 `.env.example` 中标注「需自配防火墙」。
- **重新评估的条件**：任何对外暴露场景。建议前置反向代理做 TLS。

### L5. Webhook / 通知渠道密钥明文存储

- **现状**：`output/.trae-api/notify-settings.json` 里的渠道密钥（webhook Bearer、
  Telegram Bot Token 等）以明文存放，且 `GET /v1/admin/notify/settings` 原样返回给
  管理面板（不做掩码）。
- **为什么这样**：与账号凭据不同，通知密钥无需加密解密往返（只用于出站构造），
  且备份模块已把它当作「敏感文件」加密备份。
- **已知不足**：管理会话一旦被攻破，这些密钥同时泄露。建议改为「已配置」掩码回显。
- **重新评估的条件**：面板需要支持多用户，或通知密钥需要第三方托管。

## 二、可靠性与部署形态

### R1. SQLite 单连接、无 WAL

- **现状**：`node:sqlite` 的 `DatabaseSync`（同步 API）单连接，仅设
  `busy_timeout=5000`，未启用 WAL。每次查询都阻塞事件循环。
- **为什么这样**：单机单进程的负载下，同步单连接的吞吐足够（实测 1000 账号
  `store.list()` 约 27ms）；WAL 会带来额外的检查点文件与恢复复杂度。
- **已知不足**：转发热路径每次选号会全表读；高并发时会出现秒级停顿。
- **重新评估的条件**：账号数 > 1000，或需要支撑高并发客户端。

### R2. Windows 服务（Session 0）下账号轮换不能拉起客户端

- **现状**：账号轮换依赖启动 WorkBuddy 桌面客户端的进程交互。在 Windows 服务
  形态（Session 0）下，`execFile` 被明确拒绝，`startClient` 必然失败 ——
  代码注释已承认这一点。此时轮换仍会改写 auth 备份文件，但活跃度不会记上，
  客户端也不会真正被拉起。
- **为什么这样**：该功能在**前台运行**（直接 `node src/index.js` / 交互式用户
  会话）下是正常的。仅服务形态受限。
- **重新评估的条件**：需要在服务形态下做客户端唤醒（需计划任务 + 会话交互）时。

### R3. 定时任务跨进程靠文件锁，防的是「同时跑两份」不是「重复触发」

- **现状**：`.trae-api/scheduler.lock` 保证同一时刻只有一个进程调度。
  但进程重启后，「上次运行时刻」不跨进程持久化，因此**在时刻点前后重启**
  仍可能重复触发一次（如备份、轮换）。
- **为什么这样**：签到是幂等的；备份重复只多一个文件；轮换重复影响有限。
- **重新评估的条件**：某类任务出现「重复执行造成真实损失」时，为该任务单独加
  「上次成功运行时刻」持久化。

### R4. 流式读取无空闲超时

- **现状**：上游 HTTP 超时（600s）在**响应头到达时**被清除，流式读取阶段没有
  单独的空闲超时。极端情况下 `reader.read()` 可长时间挂起。
- **为什么这样**：长输出场景下（如超长代码生成）单块间隔可能很长，固定超时容易
  误杀。
- **可调项**：`STREAM_IDLE_TIMEOUT_MS`（可选，默认关闭）。
- **重新评估的条件**：需要兜底时设为 120s 级别。

## 三、功能取舍

### F1. 成长中心无手动操作入口

- **现状**：面板只读展示成长任务状态；旅行/领奖/兑换/抽奖全部由后台定时任务执行
  （`GROWTH_POLL_ENABLED` / `GROWTH_POLL_INTERVAL_HOURS`，默认每 4h），结果经通知
  播报。
- **为什么这样**：手动操作面板是同一后台 job 的第二入口，且让「网关」界面出现
  抽奖/稀有度等游戏元素，损害产品定位。需要手动干预时用 CLI 或临时调大轮询频率。
- **重新评估的条件**：确实需要逐账号干预时，可加一个「仅本次」的确认式入口。

### F2. 模型降级（model-fallback）未实现

- **现状**：原 `model-fallback.json`（含降级映射与 `autoFallback`）从未被任何代码
  消费，已于 3.1.0 删除。若检测到该文件仍存在，启动时给出警告。
- **为什么这样**：一份「看起来生效实则从未生效」的配置文件比没有更危险。
- **重新评估的条件**：真正需要多上游降级时，应作为新功能从零设计并接入面板。

### F3. `TOOL_PROTOCOL` 仅用于展示

- **现状**：该 env 决定工具调用协议形态，但当前只被读入 config 并在配置面板显示，
  **没有行为分支**。工具调用形态由上游返回决定（网关归一化三种上游形态）。
- **为什么这样**：保留兼容位，避免旧配置报错；展示它会让用户误以为切换它有效。
- **重新评估的条件**：要在请求构造处真正支持 text 协议时。

### F4. 密钥 `resources` / `scopes` 不在面板显示

- **现状**：访问密钥后端支持按模型/平台收窄权限（`resources`），但面板创建的密钥
  统一为全平台（`platform: all`）且不展示已有的细粒度权限。
- **为什么这样**：单人使用场景下，「一把全平台密钥」够用；细粒度权限管理是
  多用户/对外分发场景的需求。
- **已知安全状况**：资源 ACL 校验本身是生效的（越权会 403），只是面板不暴露入口。
- **重新评估的条件**：需要给第三方分发受限密钥时。

### F5. Qoder 国际版对话转发已启用（单账号）；国内版与 ZCode 仍未启用

- **现状**：
  - Qoder **国际版**已开放转发：`POST /v1/qoder/chat/completions`，
    `capability.chat=true`，可调用模型以 `src/qoder/chat.js` 的
    `CALLABLE_INTL_MODELS` 实测清单为准（8 个）。
  - Qoder **国内版**与 **ZCode** 仍未启用，账号不可能被转发池选中。
- **为什么只开国际版单账号**：
  - ZCode：messages 通道按设备指纹 + 追踪头识别客户端，头形态写错会触发上游 3012
    「unusual activity」真风控。
  - Qoder 国内版：同路径实测 **503**，必须走 COSY 老协议（RSA 包裹密钥 + MD5
    签名 + 自定义 Base64 请求体）才能对话，实现成本高且同样未经多账号验证。
  - Qoder 国际版：新版协议（`api2-v2.qoder.sh/model/v1/chat/completions`）纯 Bearer、
    OpenAI 兼容 SSE，单账号实测打通；但**未验证多账号并发与限流阈值**，
    因此 `pickChatAccount` 刻意只取一个账号，不做轮询/择优。
- **已知边界（国际版）**：
  - 上游**不返回结构化 tool_calls**——传 `tools` 后模型把调用写成普通文本，
    `finish_reason` 仍是 `stop`。网关不做文本→tool_calls 的启发式改写
    （误判会让 agent 执行一个并未发生的调用）。需要工具调用请用 Trae/WorkBuddy 池。
  - `is_free=true` 不等于可调用：`qfmodel`（Qwen3.8-Flash 限免）实测
    `invalid_model_error`；`efficient` 实测 429 `provider_error`。
- **重新评估的条件**：用独立小号做并发 + 长时间压测，确认无风控触发后再做多账号负载；
   国内版需先实现 COSY 对话签名（目录签名已在 `src/qoder/catalog.js` 落地可复用）。
   详见 `docs/02-technical/channels/qoder-integration-guide.md`。

### F6. Qoder 积分任务在非 UTC+8 时区需手动对齐时刻

- **现状**：定时任务默认本地时区 10:15 执行；上游规则是「每日 10:00（UTC+8）刷新」。
- **为什么这样**：调度器只支持本地时刻，无法表达「UTC+8 10:00」。
  默认值对 UTC+8 部署是准确的；其它时区需用户按 `QODER_REWARD_HOUR` / `_MINUTE`
  或 `POST /v1/qoder/settings` 调整，否则会早于刷新拿到空列表或错过当日。
- **重新评估的条件**：部署机时区固定且非 UTC+8 时，在部署文档里写明应对齐到的本地时刻。

### F7. Qoder 本机凭据导入仅 Windows 可用（跨机请改用手动粘贴 token）

- **现状**：`src/qoder/crypto.js` 的 DPAPI 解密依赖 `powershell.exe` +
  `[System.Security.Cryptography.ProtectedData]`，非 Windows 直接报错。
- **为什么这样**：Qoder 桌面客户端只在 Windows 上分发凭据文件，DPAPI 密文绑
  CurrentUser，换机器/换用户本就解不开。
- **规避方式（不是重新评估）**：上游只认纯 Bearer 的 `dt-` token，凭据本身可移植，
  Linux 服务端或跨机接入用 `POST /v1/qoder/manual/import` 粘贴 token / 凭据 JSON
  （realm 显式指定、默认在线验证）。面板「接入 Qoder」弹窗里切到「手动粘贴 token」。
  **token 怎么取**：在能解开 DPAPI 的那台机器上、用当初登录 Qoder 的那个 Windows
  账户跑 `node scripts/ops/export-qoder-token.js`（单文件、只读、不发网络请求），
  详见 `docs/02-technical/channels/qoder-integration-guide.md`「怎么从客户端机器上取出 token」。
  注意这条路**没有自动续期**（`drt-` refreshToken 不随 token 发放），
  `dt-` 约 30 天到期后需重新导出。
- **重新评估的条件**：无需评估——本机扫描的定位就是「同机 Windows 的便捷路径」，
  跨机场景已有手动导入承接。

### F8. 通用 OpenAI provider 的流式透传未做形状判定

- **现状**：自配的 `type: "openai"` provider（用户填 baseUrl + apiKey）走
  `model-router/dispatch.js#dispatchOpenAIStream`，**逐字节原样透传**上游响应体。
  若该端点无视 `stream: true` 回完整 JSON，客户端会在 SSE 流里收到裸 JSON，解析失败。
  内置的 Trae / WorkBuddy 两条路径都已加形状闸门（零 SSE 事件即抛
  `UPSTREAM_NOT_STREAM`，见 `src/lib/sse-sniff.js`），**只有第三方透传路径没有**。
- **为什么这样**：透传路径的契约就是"原样转发"，加判定需要缓冲首帧、且会把
  「上游自定义帧格式」也判成异常。而 Trae/WorkBuddy 是实测会飘的两条车道，
  第三方端点由用户自己配置、没有出现该形态的证据。
- **重新评估的条件**：该 provider 出现一次「客户端解析失败/收到裸 JSON」的报障，
  即按 `src/lib/sse-sniff.js` 的同一判据在透传路径前面加首帧嗅探。

### F9. `AUTO_CONTINUE` 对虚拟模型不生效

- **现状**：`AUTO_CONTINUE=true` 时，只有直连模型（`/v1/chat/completions` 且未命中虚拟模型，
  走 `routes/openai.js`）会在上游截断后续写；**虚拟模型（`vm/*`）不会**。
  原因：`model-router/index.js` 曾 `require('../transform/continue')` 却从未调用，
  该路径压根没有续写分支（死导入已删除，但续写本身仍未接入）。
- **影响**：虚拟模型遇到 `finish_reason: length` 时直接把截断结果交给客户端，
  客户端需自行处理续写。实测截断发生率仅 0.06%（21/33,519 行），故实际影响很小。
- **为什么没顺手补**：续写需要把已产出的内容缓冲后再决定是否再发一轮（已发出的半截
  内容无法撤回），而虚拟模型路径刚接入「答案提交闸门」（`stream-gate.js`），
  两者叠加需要重新梳理提交语义，不适合在同一批里顺带做。
- **重新评估的条件**：`finishReason: length`／`truncated` 的比例超过 1%，
  或用户报障「长回答被截断且客户端没续写」。

### F10. 渠道清单端点在请求路径上做本机磁盘探测

- **现状**：`GET /v1/admin/channels` 每次调用都会探测本机客户端（Qoder 扫双区域
  应用目录、WorkBuddy 读 auth 文件、ZCode 判断凭据文件是否存在）。
  都是本地读、不发网络请求，但它们是**同步**的请求路径代码。
- **为什么这样**：卡片的价值就在「这台机器上到底能不能接」。把探测结果缓存起来
  就要回答「缓存多久、什么时候失效」，而客户端登录/登出没有事件可订阅；
  面板只在进入页面、手动「重新探测」与写操作后调用它，
  60 秒的余额轮询**刻意不带它**（见 `CredentialsPage.tsx#reloadAll` 的注释）。
- **重新评估的条件**：单次探测耗时超过约 50ms（Qoder 的双目录扫描在慢盘上最可能），
  或该端点出现在请求量占比统计里。

### F11. 声明了活动领取能力但没有运营面板的渠道会降级提示

- **现状**：若将来新增一个 `capability.rewardClaim = true` 的渠道而没写对应的
  运营面面板，卡片与行内的「领取」按钮会打开一个只说明「该渠道还没有操作界面，
  请先用 API」的弹窗。
- **为什么这样**：这是**刻意**的降级——比按钮不出现（用户以为功能不存在）或
  打开空白弹窗都好。渠道接入向导侧同理：没注册向导的渠道会显示
  「此渠道暂无接入向导」而不是静默消失（ZCode 当初就是这样静默了）。
- **重新评估的条件**：无需评估；新增带运营面的渠道时补面板即可，
  `src/test/channels.test.js` 会先因为「接入方式没有向导落点」而失败提醒。

### F12. Raccoon 只提供扫码登录，短信登录未做

- **现状**：`/v1/raccoon/login/session` 只走「本地生成 code + 面板渲染二维码 +
  微信扫码 + 轮询」。`send_sms` / `login_with_sms` 两条端点**未接入**。
- **为什么这样**：`send_sms` 需要阿里云滑块的 `captcha_param`（`SceneId=1pkmy0x3`、
  `prefix=hk1r5l`），那是一套独立的验证码基础设施；扫码路径完全不需要它。
  在能扫码时给用户多一条需要滑块的路径，只会多一个失败面。
- **影响**：没有微信的部署无法登录 Raccoon。
- **重新评估的条件**：出现「有 Raccoon 账号但无法使用微信」的实际需求；
  届时先解决滑块（可参考 ZCode 那条阿里云求解器，但**不要**假设两者同源）。

### F13. Raccoon 对话面不做图片缩放，超 10MB 请求体即 413

- **现状**：图片原样透传给上游。上游对**请求体字节**卡
  `HTTP_413: request body exceeds 10MB`（不是视觉 token，也不是像素）。
- **为什么这样**：参考项目有一套按字节目标缩放的链路（640k 像素 / 512KB 每张、
  base64 膨胀 4/3 ⇒ 10MB 约放 14 张）。那是一套独立的图像处理与预算逻辑，
  而 RelayGate 的调用方是否发图、发多大由客户端决定。
- **影响**：多图请求（例如一次带 4 张 2560×1600 截图）会拿到 413，错误如实透传。
- **重新评估的条件**：出现实际的多图使用场景，或客户端报障「发图就 413」。

### F14. Raccoon 远端模型目录未经真实请求验证

- **现状**：`GET /api/web/llm/v2/model_catalog` 的响应解析（`name` 作模型 id、
  `visible:false` 过滤、`billing_*` 倍率、`params.context_window|max_tokens`）
  **照抄参考实现**，本仓库未用真实登录态验证过。本机没有已登录的 Raccoon 账号。
- **兜底行为**：拉取失败或解析为空时回退到 6 条实测兜底表（带窗口与上限），
  并在响应里把 `source` 标成 `fallback`，面板据此显示「倍率可能不是最新」——
  **不假装拿到了远端目录**。
- **重新评估的条件**：用户扫码登录成功后，对比面板显示的模型清单与倍率
  是否与官方客户端一致；不一致则按真实响应修 `parseModelCatalog`。
- **另注**：Raccoon 与 Qoder 的对话面模型**只有通用密钥（`platform=all`）可调**，
  `.env` 的 `API_KEY` 在 bootstrap 时是 `platform=trae` 的专用密钥，
  **不能**用来调它们。这是与 Qoder 一致的既有边界（防止平台密钥越界消耗别家积分），
  不是缺陷，但第一次用会撞上，故记在这里。
