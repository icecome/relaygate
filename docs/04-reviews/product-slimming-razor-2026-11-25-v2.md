# Hai Razor：RelayGate 产品功能梳理与瘦身专项审查（v2 修订）

> 审计日期：2026-11-25 · 基线：当前工作树（v3.1.0，`package.json`）· 视角：产品经理 + 剃刀裁决
> **v2 修订**：采纳使用者反馈，撤销 v1 对成长中心的两项错误裁决（“立即执行一轮直接下线”“游戏化字段 Replace”）。v1 文件保留作历史记录，本文件为最终版。

## 0. v2 修订记录：撤销的两项裁决

| v1 裁决 | 撤销原因（代码事实） | v2 裁决 |
|---|---|---|
| D1「立即执行一轮」按钮 + 轮询机 → 直接下线 | ① 自动与手动**共用同一个 `runAccount()`**（`growth-auto.js:64`；自动入口 `growth-auto.js:291`，手动入口 `growth-progress.js:94`），确是同一套逻辑；② 但当前自动任务是**每天一次**（默认 08:00，`scheduler-settings.js:23-29`、`scheduler.js:970-978`），不再是每 4h；③ `scheduleCatchup` 只补“错过时刻”，**不补“执行了但失败”**——自动失败当天无自动重试，手动补跑有真实价值；④ 手动执行**不写 `growth-last-run.json`**，面板“上次运行”不会更新，是反馈缺陷而非入口冗余 | **Keep + Replace**：保留按钮与进度轮询，改为“补跑”语义，补上定时时刻提示，修 last-run 不更新 |
| 游戏化字段（Buddy / 稀有度 / 能量 / 补登卡 / 抽奖机会）→ Replace 去游戏化 | 这些是 WorkBuddy **上游真实活动**，`growth-auto.js:6-14` 明确它们产出 `+credit` / `+energy`，是“还有多少额度”这条核心价值的上游来源之一；不是 AI 编造的装饰。保留上游术语有助于用户对照上游界面 | **Keep**：字段与术语均保留，不去做措辞替换 |

> 方法论教训：v1 把“看起来像游戏”误当成“没有业务价值”，且把历史审查里的“每 4h”结论当成了当前事实。剃刀只剃**没有归属的责任**，不剃**长得不像核心功能的核心功能**。

## Verdict

- **裁决**：保留核心 / 合并少量 / 延后若干 / 删除死配置与零引用代码 / 替换少量 / 先证明若干
- **一句话理由**：RelayGate 的核心闭环（接入账号 → 稳定转发 → 看额度与成本 → 排障）以及支撑它的额度获取链路（WorkBuddy 成长活动）都值得保留；真正该剃的是**死配置、零引用导出/字段、一次性入口的过度导航**——而不是长得像游戏、实际在产积分的上游活动。
- **剃刀原则**：每个功能必须挣得独立存在——删除它会破坏真实用户目标、抹掉真实区分、隐藏真实风险、或把不可避免的复杂度推给更差的归属。只因习惯、对称性、想象中的未来或“网关应该都有”而存在的，一律砍、合并、延后或要求举证。
- **未审范围（防误砍）**：`node_modules/`、`web/dist/`、`logs/`、`output/`、`backups/`、`design/`、`.history/` 等运行/构建产物；`docs/` 与 `scripts/` 仅作证据，不裁其存在性；视觉风格、移动端断点、安全漏洞整改属其他审查线（见 `docs/04-reviews/code-audit-2026-11-25/`），本轮只裁**功能存在性**。

### 1.2 产品真实定位（由代码而非 README 得出）

- 唯一用户：机器主人本人；默认 `127.0.0.1:19900` 本机进程（`README.md:7-9`）。
- 真实价值排序：① 还有多少额度 → ② 账号有没有死 → ③ 转发有没有出错 → ④ 接入新账号 → ⑤ 偶尔改签到时间。
- **额度来源不止“池里剩余”**：WorkBuddy 成长活动（派猫旅行、连登兑换、任务领奖、抽奖、Buddy 盲盒）会实际产出 credit / energy（`growth-auto.js:6-14,97-281`）。因此成长中心属于价值排序 ① 的**上游供给链路**，不是独立的游戏模块。

### 1.3 访问行为的证据边界

**本项目没有埋点/用户访问日志**。本次以 `logs/*/traffic.jsonl` 的文件存在性、代码中的入口层级（侧栏/折叠/二级 tab）、以及单人自托管场景的合理行为作为**推断证据**，并明确标注置信度。凡涉及“打开频率低于 5%”的判定，均属于**产品判断/待证明**，不把它伪装成真实统计数据。

## 5. 必须保留的复杂性（绝对不要碰）

| 复杂性 | 为什么必要 | 越过哪里开始伤害 |
|---|---|---|
| 成长自动化的 `client_token` 幂等键（日粒度 / 账号+目标日期） | 补跑、重跑不重复入账；补登卡多张互不吞掉 | 不要为“简化”改用当天单一 seed |
| 积分口径 vs ZCode token 口径分离 | 把 1e8 token 当积分求和会让成本全错 | 不要统一单位，不要做“相加”便利函数 |
| `unlimited` 独立于 `remaining` | “不限量 ≠ 0”；显示成 0 会被误读为无额度 | 不要折叠成一个数字 |
| `isLoginKeyRejection` 区分两类 401 | 管理密钥失效与转发密钥失效语义不同 | 不要合并成 `if (status===401)` |
| 请求取消（AbortSignal 贯穿） | 路由切换后旧响应不能覆盖新数据 | 不要删 signal 透传 |
| 定时任务跨进程锁与幂等 | 防重复备份/轮换 | 不要“简化”成无锁调度 |
| `stream-gate` 与错误帧 | 防止错误被当模型输出 | 不要用统一 try/catch 抹平 |
| 精确/估算/无计量三拆、Trae 滞后判断 | 成本信任的根基 | 不要让 UI 隐藏口径来源 |
| 登录密钥一次性明文展示与 `safetyBackup` | 泄露面与不可撤销操作的护栏 | 不要改成持久明文或免确认 |

## 7. 风险评估与护栏

### 7.1 行为保持闸门

| 改动 | 必须保持的可观察行为 | 验证命令 |
|---|---|---|
| D1 删 `TOOL_PROTOCOL` 展示 | 工具调用形态仍由上游响应归一化，三协议出口不变 | `npm test && npm run lint` |
| D2/D3 删零引用导出/字段 | 页面渲染与 API 响应不变；TS 编译零错误 | `npx tsc -b --force && npm run lint` |
| F1/F2 文案与提示 | 手动补跑仍调用同一 `runAccount`；自动任务不受影响 | `npm run test:growth && npm run build:web` |
| F3 手动写 last-run | 自动与手动写入不互相覆盖；并发 `running` 锁仍生效 | 新增/运行 growth 相关测试；检查 `startAuto` 的 409 分支 |
| H1 合并客户端接入 | 首次接入说明仍在一屏内可达 | 手工点一遍首登流程 |

### 7.2 可能的反弹与护栏

- **最可能的反弹**：因为“仪表盘里出现 Buddy/抽奖”而再次提出删成长面板。→ 护栏：在 `known-limitations.md` F1 补充一句“成长活动产出 credit/energy，是额度上游供给；面板字段来自上游真实活动，不是装饰”，把判断依据固化。
- **误砍风险**：删 `TOOL_PROTOCOL` 时不能删 `config.js` 的读入——旧 `.env` 里有该变量时应静默兼容。
- **口径漂移风险**：删零引用类型字段时，若后端某日启用同名字段，前端会静默丢弃。→ 护栏：留 deprecated 注释或保留可选字段。
- **回归风险**：F3 涉及写 `growth-last-run.json`，必须确认不破坏 `scheduleCatchup` 的当日判据（它读的是 `dailyRunState`，不是 last-run，二者独立）。
- **注释漂移**：`GrowthPanel.tsx:4` 的“每 4 小时”必须随 F2 一起改，否则下次审查还会重复本次误判。

### 7.3 执行顺序建议

1. **F1 + F2**（文案、提示、注释修正）→ 零风险，先做，消除“自动在跑但用户不知道”的认知问题。
2. **D1 + D2 + D3**（死配置 + 零引用）→ 一次提交，`tsc` + `lint` 把关。
3. **F3**（手动补跑写 last-run）→ 独立提交，加测试。
4. **H1**（客户端接入合并）→ 独立提交，手工验收首登。
5. **O1** 维持不变；Prove-first 项先取证，**不要在本轮直接删后端端点**。

## 8. 一句话结论

> RelayGate 的核心功能与 WorkBuddy 成长活动（真实产出 credit/energy 的额度供给链路）都值得保留；真正该剃的是**死配置、零引用代码和一次性入口的过度导航**。成长面板该做的是**补提示、修正过期注释、修好补跑反馈**，而不是下线——这是 v2 采纳使用者事实后的最终裁决。
