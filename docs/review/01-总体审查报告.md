## 3. CRITICAL 问题详情

**本轮无 CRITICAL 级发现。**

**为什么 M-S1（首登端点跨源可写入）不判为 CRITICAL：** 探针实测确认恶意页面可成功创建 login key（HTTP 201），但响应头 `Access-Control-Allow-Origin` 为 `null`，跨源 JS 只能拿到 opaque response，**读不到明文密钥**。因此该缺陷的后果是「首登被抢占 → 合法用户被 403 拒绝 → 需跑 CLI 重置」，属可用性/拒绝服务性质，不构成账号接管。详见 M-S1。

## 9. 做得好的地方

1. **凭据加密的失败模式被认真对待。** `lib/crypto.js:10-13` 明确写出「旧密钥文件存在时绝不允许走生成分支」，因为重新生成会导致所有已存账号不可解密且不可逆；`getEncryptionKey`（34-58 行）在无法持久化时选择抛错而非静默随机。这是把「不可逆」当回事的写法。

2. **原子写入的推理完整。** `lib/atomic-write.js:9-15` 解释了「覆写不是原子的 → 进程在 truncate 后被杀会留半截 JSON → 下次启动静默回退默认值 → 用户配置丢失」，并说明为何必须同目录 `rename`（跨设备会退化为 copy+unlink 失去原子性）、为何必须 `fsync` 后再 rename（否则断电留下空壳）。

3. **状态文件路径迁移有兼容策略且被测试守门。** `lib/paths.js` 头部完整记录了两个真实后果（测试污染真实配置已实际发生过一次；部署搬迁丢设置），规则统一为「写新位置、读时回退旧位置」；`crypto.js:47` 与 `backup.js:120` 在从旧位置读到密钥后顺手复制到新位置，同时**保留旧文件不删**以便回退旧版本代码。

4. **确定性错峰替代随机打散。** `lib/util.js:59-87` 的 `planSpread` / `runPlanned` 把偏移绑定到 `(salt, 条目键)` 而非调用时刻，因此同日重跑落在同一时刻、可重放、幂等；`deterministicOffsetMs` 选 FNV-1a 而非 `hashCode` 并给出理由（账号 id 前缀相似，FNV 雪崩性更好）。
