# WorkBuddy 成长计划连登 28 天检查与补登（2026-10-30）

## 目标

检查项目 RelayGate 里所有启用的 WorkBuddy 账号「成长计划（成长中心）」的本月连登天数是否已满 28 天；不满 28 天的账号把所有补登卡用掉，再尝试领取 28 天档位奖励。

判定口径以本机真实 token 实测（2026-10-30 22:2x–22:4x Asia/Shanghai）为准：

- `GET /activity/growth/streak` 的 `streak.days` / `streak.month_total_days` = 本月已点亮天数；
- `redemption_status.tier_28d_status`：`locked` = 天数不足，`available` = 可领取，`claimed` = 本月已领；
- `GET /activity/growth/heatmap` 的 `cells[].score`：本月 `score == 0` 的日期是真正的断登日（`today` 字段里的当天 0 分不代表断登，当天还可靠真实活跃点亮）；
- `/streak` 的 `makeup_dates` **不可靠**：补登成功后仍然列出已补日期，本次实测补登 `2026-10-03` 成功后该列表反而变成 `["2026-10-03","2026-10-28"]`，即"已补的也列在里面"。所以它不能作为"还能补哪几天"的来源。

## 执行方式

新增一次性脚本 [scripts/growth-28d-check.js](../scripts/growth-28d-check.js)（复用 `src/workbuddy/cat-trip.js` 上游客户端与 `src/auth` 的账号凭据）：

```bash
node scripts/growth-28d-check.js          # 只读检查
node scripts/growth-28d-check.js --apply  # 用掉补登卡 + 领 28 天档位
```

用卡时**不传幂等 seed**：每张补登卡是不同日期上的独立手动动作，需要各自独立的 `client_token`（若按"账号+日期"派生 seed，同一账号同一天内多次写会拿到同一个 key，上游去重后只会生效一次）。

相关已有脚本：[scripts/ops/wb-growth-makeup.js](../../scripts/ops/wb-growth-makeup.js) 也能补登（`--date` 指定日期、`--each` 每号一补，同样不带 seed），其注释已记录 makeup_dates 与 heatmap 不一致的问题；但它只做"补最近一次漏签"，不判断连登口径、不领 28 天档位，故本次另写端到端脚本。

### 补登方向的关键结论（重要）

28 天档位按**连续登录天数**判定（`remaining_days == streak.days`），不是"本月累计"：

- 实测账号 `18932771517`：连登段 10-04..10-30（27 天），0 分日为 10-01/02/03。
- 脚本第一次按"最早断登日优先"补了 `2026-10-01`（孤立断登日）→ 本月累计 28，**连登仍 27**，档位依旧 `locked`，redeem 仍 403。
- 随后手动补 `2026-10-03`（连登段起点前一天）→ 连登 28，档位转 `available`，领奖成功。
- 同理 `17395025927`：补 `2026-10-03` 后连登 28 并领到 credit +150 / energy +5。

脚本已修正为：**只补 0 分日里最晚的那个**，即从当前连登段起点逐日向前延长。孤立断登日补了也不解锁档位，纯粹浪费补登卡。

## 发现的问题与修复（2026-11-02 已落地）

以下原为「建议后续修」，现已在 `src/jobs/growth-auto.js` 补登段修复，并以 `src/test/growth.test.js` 的 makeup / fetchHeatmap 用例固化契约：

1. **补登幂等键**：此前与其余动作共用「账号+当天」种子，同一天用第二张卡时 key 相同、被上游去重静默吞掉。现改为按「账号+目标日期」派生——重跑同一天仍去重（不重复消耗），不同日期互不吞掉。
2. **候选日来源**：此前只信 `/streak` 的 `makeup_dates`（该列表在补登成功后仍包含已补日期，又不包含真正断登日，本次 8 个账号全被它误导成「候选日本就已签」）。现改以 `/heatmap` 的 0 分日为准，**从新到旧**补（最新 0 分日就是连登段起点前一天，最能延长连登；孤立早断登日补了也进不了 28 个连续格子），`makeup_dates` 仅在 heatmap 查询失败时兜底。为此新增 `fetchHeatmap()` 只读客户端。
3. **每轮用量**：`MAKEUP_MAX_PER_RUN` 从 1 提到 8，补到「最低未领档位要求天数」即停；三档全 claimed 时不耗卡；档位查询失败时本轮不用卡（判不了缺口就不动卡）。

验证：`node scripts/ops/growth-auto-dryrun.js` 拦截全部写接口空跑真实 8 个账号，决策正确（11 月新月份仅对有卡的 4 个账号提案补 11-01 这个真实 0 分日，幂等键已是 `账号|makeup|日期` 形态；无卡的 4 个不动作）。

4. 一次性运维脚本仍保留在 `scripts/growth-28d-check.js` 可重复执行；固化能力已由第 1–3 项在 `growth-auto.js` 内完成。
