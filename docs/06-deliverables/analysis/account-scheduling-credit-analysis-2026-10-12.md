# RelayGate 账号调度与积分消耗分析报告

- 日期：2026-10-12
- 范围：账号池 FEFO 调度、模型路由、余额/权益包快照、近 30 天消耗数据
- 触发问题：用户观察到「权益包到期时间排名较低的账号，积分消耗反而更多，甚至超过排名在它前面的账号」

---

## 1. 现状梳理

### 1.1 调度架构（两层，互相不感知）

```
客户端请求 (vm/long-context 等)
   │
   ▼
模型层  model-router/orderCandidates()          ← 不感知账号权益
   │   自动分层 VM：sort=rate 按模型倍率升序，
   │   取前 rotateTopN 个做加权轮转（weight 抽签）
   ▼
候选模型（决定平台：trae 池 / workbuddy 池）
   │
   ▼
账号层  credentials/pool.pick()                 ← FEFO 在这里
        仅在该平台的 8 个账号内排序：
        priority置顶 → FEFO到期时刻 → 同刻临期金额
        → d3/d7 → costTier → 余额 → 闲置时间
```

- FEFO 实现于 commit `88bd5eb`（2026-10-06）「实现自动分层模型路由与FEFO账号调度机制」。
- 排序信号来自 `entitlementSnapshot.packs` 的 `summarizeFefo()`（src/credentials/credits.js）。
- **跨平台（trae 池 ⇄ workbuddy 池）之间不存在任何全局排序**。

### 1.2 节流参数（决定 FEFO 的实际生效范围）

| 参数 | 值 | 含义 |
|---|---|---|
| RATE_PACE_MS | 5000 | 同账号两次请求最小间隔 |
| RATE_WINDOW_MS / MAX | 30000 / 2 | 同账号 30s 窗口最多 2 次（≈4 次/分钟） |
| MAX_IN_FLIGHT_PER_ACCOUNT | 2 | 同账号并发上限 |
| rateCooldownMs | 20000 | 429 后冷却，指数退避至 30min |

单平台 8 账号理论容量 ≈ 32 请求/30s。

## 2. 5W2H 根因分析

**What**：FEFO 排名靠后的账号消耗高于靠前账号（如 cn 池排名 3 的 15833374517 今日耗 875 积分，排名 1 的 18103270786 仅 184）。

**Why（四层原因，按权重排序）**：
1. FEFO 只在单平台池内生效；跨池流量分配由模型层按「模型倍率 + 加权轮转」决定，与账号权益无关。按手机号跨平台对比消耗本身不成立。
2. 负载 ≥ 容量时（今日峰值实测 32 请求/30s），排名 1 的账号被节流（5s 间隔 / 2次30s / 并发2 / 模型级冷却），请求必然溢出到排名靠后的账号，调度退化为近似轮转。日志中大量 `[pool] rate_limit on acct_…, switching` 佐证。
3. 【缺陷】余额自动刷新被关闭（`BALANCE_REFRESH_ENABLED=false`，relay.out.log），权益快照每天仅 00:50 签到链刷新一次。白天 FEFO 用的是凌晨快照：白天作废的包仍占 soonest 名次（僵尸第一名），白天用尽/新领的包不反映。
4. 【放大器】单次请求成本方差极大（vm/long-context 单次 9~11 万 token，0.2~1+ 积分 vs 普通请求 0.01 级），低排名账号接到 2~3 个大请求即反超；sticky 会话（1h TTL）绑定期间完全绕过 FEFO。

**Where**：
- 排序实现：src/credentials/pool.js:466-497（pick）
- FEFO 计算：src/credentials/credits.js:75-108（summarizeFefo）
- 模型层排序：src/model-router/index.js:83-133（orderCandidates）
- 快照刷新：src/jobs/balance-refresh.js（enabled=false）、src/upstream/balance.js

**When**：FEFO 于 10-06 上线。此前的排序是纯余额优先（least_balance）；上线后余额降为末位兜底。快照陈旧问题自 balance-refresh 被关闭起持续存在。

**Who**：所有走账号池的转发请求（vm/* 虚拟模型、直连模型、探活 probe、admin-debug）。

**How**：pick() 每次请求重排 → 第一个通过「启用/冷却/节流/余额/并发」过滤的账号胜出。FEFO 只影响「谁第一个被试」，不影响「谁最终被用」——节流与 sticky 决定后者。

**How much**：今日 trae 池真实消耗 1,272.97 积分（used_total 差分）；wb 池 remaining 差分 ≈680（含包作废水份，口径不可信，见 §4）。量级上无泄漏，属于分配偏差而非损失。

## 4. 附带发现的观测缺陷

1. **vm 路径日志无法审计账号归属**：model-router/index.js:314 的 `logRequest({ account: cand.id, … })` 记录的是候选模型 ID（如 `workbuddy/wb/deepseek-v4.1-flash`）而非池账号 ID（`acct_…`）。dispatch 返回值里有真实 accountId，但未透传。→ 账号级消耗分布只能靠余额快照差分反推。
2. **WorkBuddy 消耗口径失真**：wb 快照不写 used_total（upstream/balance.js:177-181 `used: null`），只能用 remaining 差分，被包到期作废污染（credit-history.js 注释自认实测可达官方账单 80 倍）。
3. **直连路径与 vm 路径的 account 字段口径不一致**（直连记 `req.accountId`，vm 记候选 ID）。
4. **日志目录多处并存**：traffic.jsonl 在 `logs/YYYY-MM-DD/`；而 `.trae-api/stats-cache`、`official-usage-cache`、`trae-usage-cache` 各自缓存按日聚合，刷新停摆后这些缓存与流量日志互相矛盾（面板「消耗」读缓存、本文读快照差分）。

## 5. 关联影响分析

- **调用链**：pool.pick ← pool.run ← dispatch(dispatchStream/NonStream) ← model-router.handleChat ← routes/openai.js / anthropic.js / responses.js；另有 scheduler(model probe)、admin-debug、rotate 等旁路消耗。
- **数据流**：entitlementSnapshot 由 refreshBalance（每日 00:50）写入 → 被 pick 的 FEFO、snapshot 面板、credit-alerts 三方消费。刷新停摆时三处同时陈旧。
- **耦合点**：FEFO 依赖快照新鲜度；sticky 绑定绕过排序；节流参数决定排序有效负载区间；模型层 rotateTopN 决定跨池流量比例。
- **回归风险**：若直接「修」成跨池全局 FEFO，会破坏模型层按倍率选型的成本意图；若强制 sticky 失效，会伤害上游会话缓存命中率（cacheRead 占比高，成本差异 4~8 倍）。

### 跨平台账号级调度的规则

模型层选候选时，比较顺序为：

1. **tier 1（抢占）**：候选所属池内存在 `POOL_ACCOUNT_PRIORITY_WINDOW_DAYS`（默认 7 天）内到期的未用尽积分 → 按最早到期时刻升序，先到期先用；
2. **tier 2**：池内无临期积分 → 按池内**可用余额合计**降序（余额多的池优先使用）；
3. **tier 3**：池内无启用账号 → 沉底，仍保留作 failover 兜底；
4. 同一 tier 内回落到原有成本序（倍率/窗口 → priority → 轮转池加权）。

同池候选的 tier 必然相同，因此池内的倍率排序与 `rotateTopN` 轮转语义完全不变——改动只影响「跨池」的相对顺序。

开关：`POOL_ACCOUNT_PRIORITY=false` 可完全关闭，恢复旧的纯成本序行为。

### 验证方式

- **跨池抢占**：给任一账号加一个 2 天内到期的权益包，`node -e "require('./src/model-router').orderCandidates(...)"` 中该池候选应整体排到另一池之前（单元测试「候选排序：临期池整体抢占非临期池」已覆盖）。
- **#2 生效**：`logs/<date>/traffic.jsonl` 的 `account` 字段应出现 `acct_…`，可与 `credit_history` 差分对账。
- **#1 生效**：`logs/relay.out.log` 出现 `[balance-refresh] timer done ok=17 …`，且 `task-log.jsonl` 每 30 分钟一条 `balance-refresh`。
- **整体**：连续 3 天低负载时段（<10 请求/30s）内，FEFO 排名 1 的账号请求占比应 >40%。

## 7. 结论

FEFO 机制本身按设计在工作（wb 池数据可证：排名前 3 恰为消耗前 3）。用户观察到的异常由三层结构性边界（跨池无排序、节流溢出、单请求成本方差）叠加两个真实缺陷（快照刷新停摆、日志归属缺失）共同造成。

现已全部修复：跨池账号级调度落地（临期抢占 + 余额优先）、快照刷新开启、流量日志可审计、sticky 不再吞掉 FEFO、WB 消耗口径改用 used。

**遗留边界（非缺陷）**：峰值负载（今日实测 32 请求/30s ≈ 单池容量上限）下，池内节流仍会溢出到低排名账号——这是容量问题，不是排序问题，需要加账号或调 `RATE_WINDOW_MAX` 才能改变。
